A useful report, one layer down.

Start with the things you check often. Put crew, wear, and installed equipment in the systems section. Show “unknown” for missing observations.

The timer must tell the truth

  • After departure, derive remaining time from the API arrival instant. Before departure, label route duration as an estimate.
  • At zero, say “Checking arrival” until fresh navigation confirms the state. Never unlock actions from a client timer.
  • Recalculate from absolute instants on resume. Phone background timers can pause.
  • Keep UTC in storage and API data. Display the arrival in the phone's timezone and show that timezone.

Actions follow the actual situation

  • In transit, let me inspect the destination or ship.
  • In orbit, offer a relevant preview, such as docking or extraction when equipped.
  • Docked, let me inspect trade or refueling options.
  • On stale data, refresh before offering a new command.
  • For an uncertain write, reconcile the outcome before retrying. Keep the unresolved action visible.

05 / Native feeling, web foundations

Make a quick check feel complete.

Protect the first screen

Keep identity, current status, ETA, fuel, cargo, and one action in the first phone view. Let secondary details scroll in a report. Allow page growth with large text and small screens.

Keep navigation predictable

Bridge, Cargo, and Activity are stable destinations. Docking and refueling are actions inside those views. The top ship name becomes a selector later. Apple tab-bar guidance.

Use sheets for focused tasks

Open the ship report or an action preview over the current context. Include an explicit close button, trapped focus, Escape support, and focus restoration. Do not require swiping to dismiss. Apple sheet guidance.

Leave room for a thumb

Use 44px or larger controls as the design target. Keep labels readable, focus visible, and state understandable without color. WCAG 2.2 AA specifies 24px minimum targets with exceptions; this board chooses larger ones. Target size guidance.

First / Single ship

One complete daily loop

Responsive bridge, ship report, arrival and cooldown handling, cargo, recent activity, fresh/stale states, and existing command previews. Use the current dark tokens and shared command services.

Next / Fleet doorway

Switch without losing context

Turn the ship-name control into a sheet with a small sprite, symbol, role, status, and next-ready time per ship. Preserve per-ship view state. A fleet management page comes after the single-ship workflow works well.

Later / Install and host

A home-screen shortcut

Serve the web app on an HTTPS subdomain. Add a manifest, icons, standalone display, and safe-area padding. Cache static art selectively; keep private state fresh and gameplay online. Verify installation on the actual phone. WebKit home-screen app guidance.

Implementation notes for the current stack
  • Current checkout: Laravel 13, PHP 8.4, Vue 3, Inertia 3, Tailwind 4, and Vite 8. Declared by the project manifests; these are constraints, not a runtime audit.
  • Reuse AppShell.vue and resources/css/command.css tokens. Move toward a compact mobile shell with safe-area insets and dynamic viewport sizing during implementation.
  • Proposed component responsibilities: ShipBridge for composition, ShipScene for decorative state, ShipReport for details, and ShipActionPreview for approval. Keep timers and formatting shared.
  • The existing dashboard polls local Inertia state every five seconds. Animate locally between snapshots; do not send API calls per frame or per countdown tick. Refresh on visibility and reconnect with a bounded policy.
  • Reuse dateTime.js for local display and the existing server-side command checks. Keep API bearer tokens on Laravel. Give status views one observation age instead of scattering tiny timestamps.
  • Real implementation still needs small-screen Safari testing, large-text checks, focus and keyboard checks, authenticated ownership tests, and interrupted-command checks. This prototype only verifies the design artifact.

Keep the 1 GB server. Control peak memory.

Read-only SSH assessment of taylor@tayloroyer.com · November 1, 2026, approximately 13:19–13:23 America/Los_Angeles, 21:19–21:23 UTC.

There is no evidence here that you need to buy more resources. The existing workload is light on CPU and has useful memory headroom. The main risk is several PHP requests, queue jobs, and scheduled tasks becoming active together. Optimize their concurrency and idle costs before adding capacity.

No server configuration was edited, no service restarted, no package installed, and no application command or load test executed. Inspection creates normal SSH, sudo, and database activity and may produce ordinary audit logs. This report and its evidence file were saved locally.

What is running

The host reports Ubuntu 24.04.5 LTS, kernel 6.8.0-147-generic, one CPU, and 961 MiB usable RAM. It runs Nginx, PHP 8.5 FPM, MariaDB 10.11.14, Supervisor, fail2ban, and normal system services. FishCounts, Print For Me, and the portfolio each have a separate FPM pool and Unix socket.

Each pool uses pm=ondemand, two maximum children, a 15-second idle timeout, and recycling after 250 requests. This is already a sensible low-memory arrangement. Together the pools permit six simultaneous web PHP processes. Four persistent database queue workers also run: two for FishCounts and one each for Print For Me and the portfolio. All three applications have configuration and route cache files present; their freshness was not tested.

Capacity evidence

The initial snapshot showed 350 MiB available memory, 329 MiB swap in use out of 2,543 MiB, and load averages of 0.00. The 25 GB root filesystem was 45% used, with 13 GB available. The five one-second interval samples after vmstat's initial lifetime row showed no swap reads or writes and 98–100% CPU idle. Memory pressure averages were zero. No OOM events matched the available kernel journal for the requested 11-day window.

Existing sysstat records cover October 24 through November 1. Their daily CPU idle averages were 97.71–98.04%, and daily available-memory averages were about 307–358 MiB. November 1 is a partial day. Mean swap activity was low, at 0.17–0.78 pages read and 0.20–1.08 pages written per second across those daily summaries. These averages can hide brief peaks; they are not a throughput benchmark or proof that all request bursts are safe.

The four queue workers had about 248 MiB combined RSS in the initial snapshot, but shared pages make RSS sums overstate unique memory. A later proportional-memory sample measured roughly 132 MiB resident across those workers plus 27 MiB swapped. MariaDB had roughly 55 MiB proportional resident memory and 178 MiB swapped. Cold database pages explain part of the swap occupancy. Swap usage alone does not establish current memory pressure.

Recommended order of work

  1. Reduce idle queue costs where delay is acceptable. First measure queue arrival rates, oldest-job age, and busy time for the portfolio and Print For Me. If they are rarely used and can tolerate delayed pickup, replace their always-running workers with a bounded, non-overlapping scheduled drain. Each currently accounts for roughly 38–44 MiB proportional resident memory. Savings are estimates, not guaranteed reclaimed RAM. Preserve separate application users and queue ownership. Keep continuous workers for workflows requiring prompt responses, especially time-sensitive SpaceTraders actions. Do not combine queues belonging to different applications into one Laravel worker.
  2. Set a whole-server PHP concurrency budget. Keep on-demand FPM. Measure representative busy-request and job peaks before changing pool limits. A hypothetical six web children at 60 MiB private memory each would need 360 MiB, already above today's available headroom before extra scheduler work. This is a sizing scenario, not a measured web-process size. Consider one child for low-traffic pools if waiting is acceptable; verify that requests do not depend on synchronous calls to another request in the same pool. Queue memory recycling is checked between jobs, so --memory=128 is not a hard cap on a running job. CLI PHP currently has memory_limit=-1. Test finite per-worker PHP limits against real job requirements before proposing values.
  3. Review MariaDB's unused MyISAM allocation. The configured key buffer is 128 MiB, yet the engine inventory showed no MyISAM tables and key-block usage and reads were zero. A small key buffer, provisionally 8 MiB, is a strong candidate after checking all scheduled/import workloads. The configured reduction is 120 MiB, but it must not be presented as 120 MiB of resident RAM savings. The existing process is partly swapped and buffers need not all be resident. Aria also has a 128 MiB page cache; assess its utilization before considering 16–32 MiB because internal disk temporary tables may use Aria.
  4. Keep the InnoDB pool at 128 MiB initially. The server is shared with PHP. Do not apply a dedicated-database percentage-of-RAM rule. About 0.47% of recorded logical buffer reads required physical reads since database startup. This lifetime ratio does not isolate slow requests. Connections peaked at eight against a limit of 30. Leave that limit alone initially. About half the recorded temporary tables went to disk, but increasing the 16 MiB temporary-table limits could multiply memory use across connections. Investigate the responsible queries first. Slow query logging is off, so the zero slow-query counter is not proof that queries are fast.
  5. Bound system journal retention. Journals occupy 2.3 GB of the 2.5 GB under /var/log. A proposed 256 MiB journal cap could reclaim roughly 2 GB after approved retention cleanup. This improves disk reserve, not application RAM. Decide what incident history must be retained or exported before deleting it. With 13 GB free, cleanup is useful housekeeping rather than an emergency.
  6. Review optional background services last. fwupd, udisks2, and upower are running on this virtual server. Their sampled RSS totals roughly 29 MiB, with shared-memory caveats. Confirm provider and system dependencies before disabling any. Preserve security updates, fail2ban, SSH, time synchronization, and monitoring. Small service savings should follow the larger application and database decisions.

Settings that already fit this machine

Nginx runs one observed worker with gzip enabled. FPM OPcache is enabled with a 128 MiB configured cache. JIT is disabled, even though its buffer setting reads 64 MiB; that setting is not proof of a live 64 MiB allocation. Do not shrink OPcache without measuring FPM cache occupancy and restarts. CLI OPcache is off. Keep the existing swap as a safety margin; do not clear it or change swappiness merely because cold pages reside there.

Three workers already recycle after an hour with a 128 MiB Laravel memory threshold. The FishCounts external worker lacks an explicit maximum lifetime and uses unlimited retries. Review its job-level retry policy and failure handling before changing either. Lifetime recycling can be proposed independently after confirming safe restarts and job timeout versus retry-after settings.

Scheduling, backups, and SpaceTraders

Each existing app invokes its scheduler every minute. Database backups are scheduled at 03:00, 03:15, and 03:25 in the cron environment; the observed server clock reports UTC, but cron timezone overrides were not fully audited. Keep backups staggered and verify scheduler overlap protection before introducing additional background jobs. Backup scripts and restore correctness were not tested.

SpaceTraders was not among the enabled sites or observed workers. A single-operator deployment appears plausible on this host, conditional on a measured memory budget. Start with one on-demand web child and one queue worker, then account for scheduler processes and existing workloads. SpaceTraders needs its due-action dispatcher and database queue worker to continue automation. Build frontend assets locally or in CI and deploy completed artifacts to avoid build-time RAM spikes. Do not add Redis, a development server, or extra worker replicas without a measured need.

For a future approved deployment, use a provisional guardrail of at least 150–200 MiB available during representative combined workload, no sustained swap churn or memory pressure, acceptable request latency, and no growing queue age. This is a proposed operating target, not measured added-app capacity. If it fails, first reduce concurrency, stagger jobs, or reduce idle services. No requests-per-second capacity can be responsibly claimed from this inspection.
